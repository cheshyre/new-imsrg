# 30 — Testing and validation

"Numerically equivalent within reason" *(user)* is made concrete here. Correctness gates every
merge: **no feature counts as done until its tests and its comparison against imsrg-devel (or
the brute-force reference) pass.**

## 1. Test layers

| Layer | Where | What | Runs in `tools/ci.sh` |
|-------|-------|------|-----------------------|
| Unit | `tests/unit/<module>/` | Invariants and small cases for every public function | always |
| Property | same | Symmetries: [X,Y] = −[Y,X]; linearity; Jacobi identity on random ops; Hermiticity of [A,H] when A is anti-Hermitian; normal-order ∘ undo = identity; basis transform with C = 1 is the identity; unitarity of HF C | always |
| Fast vs reference | `tests/unit/commutator/` | Every optimized term against `commutator_ref` on random operators (emax 1–2, several references, including open-shell fractional occupations) | always |
| Golden (imsrg-devel) | `tests/unit/*`, `tests/integration/` | Same inputs into both codes, outputs compared (§3) | always, when golden files exist |
| Brute force m-scheme | `tests/python/` or `commutator_ref` | Independent validation of the J-coupled algebra, especially 3B (see `14-imsrg3-plan.md` §3) | emax ≤ 2, `slow` label for larger |
| Integration | `tests/integration/` (pytest) | Run the `imsrg` executable end to end and compare to golden data (§4) | yes if `IMSRG_TEST_DATA_DIR` has the files |
| MPI | `tests/integration/` (label `mpi`) | Same run on 1, 2, 4 ranks gives the same numbers | yes if MPI is enabled |
| Python | `tests/python/` | The bindings, plus small pipelines | yes if Python is built |

Random operators: generated by our own generator with an **explicit seed parameter**. imsrg++
uses a static incrementing seed, so its results depend on call order. Our generator imposes the
requested Hermiticity and the symmetries of the channel structure. The same operator is written
as an OperatorDump so imsrg-devel can read it (§3).

## 2. Tolerances *(owner-approved split, 2026-11-11)*

Deterministic **unit-level** checks stay tight: both codes do the same arithmetic, so a looser
tolerance there would only hide bugs. **End-to-end** acceptance is looser: the flows involve
thresholds and step decisions, and agreement "within reason" is enough. Always **log the actual
deviation** in test output and in the milestone report, even when a test passes. If an
end-to-end deviation exceeds 1e-5 MeV, look for the cause briefly (e.g. a different step count)
and note it in STATUS.md, but do not block on it.

| Quantity | Tolerance |
|----------|-----------|
| Wigner 3j/6j/9j, CG, Moshinsky vs sympy exact | 1e-12 relative (absolute 1e-14 near 0) |
| Read matrix elements (me2j/NO2B → pn operator) vs imsrg-devel dump | 1e-10 absolute |
| Single commutator term vs reference implementation or imsrg-devel | `max|ΔZ| ≤ 1e-10 · max(1, max|Z|)` |
| Norms, normal ordering, basis transformation on fixed inputs | 1e-10 relative |
| HF energy and SPEs (end to end) | 1e-4 MeV |
| MBPT(2)/(3) energies (end to end) | 1e-4 MeV |
| IMSRG(2) ground-state energy (end to end) | 1e-3 MeV (log the deviation and the step counts of both codes) |
| Valence-space 0B/1B/2B elements | 1e-3 MeV |
| Transformed scalar operators (e.g. Rp2) | 1e-4 fm² |
| IMSRG(3) variants at emax 2/3 (E0, triples energy) | 1e-3 MeV |
| MPI rank-count invariance | 1e-10 relative |

## 3. Golden data from imsrg-devel

Build the reference outside the repo (`20-build-and-tooling.md` §5). Then:

1. **Reference harness**: `tools/reference/refharness.cpp` is a small C++ program linked
   against the old `libIMSRG`, never part of our build. Subcommands:
   * `dump-hamiltonian`: read me2j (and NO2B) as the old driver does and write OperatorDump
     files of the bare Hamiltonian pieces (T, V2, NO2B) at a given emax and reference;
   * `hf`: run HF and dump E_HF, SPEs, C, and the normal-ordered H;
   * `commutator <term> X.dump Y.dump Z.dump`: read two OperatorDumps (same ordering
     conventions, D11), evaluate one named term, write the result;
   * `flow`: run a full imsrg++ pipeline and dump E0, the flow trajectory, and operators.
   The `imsrg++` executable itself also produces golden numbers for the end-to-end tests.
   Capture its stdout and output files.
2. Scripts `tools/reference/gen_golden_*.sh|py` produce `tests/golden/<test-id>/...`: small
   JSON for scalars, CSV for flow logs, OperatorDump for operators (only at emax ≤ 2 to keep
   the repo small; larger outputs are regenerated on demand into the build tree and are
   gitignored).
3. `tests/golden/README.md` records the exact command, parameters, and reference-code version
   for every golden file.
4. pyIMSRG (old Python bindings) may be used instead of the harness where convenient. It has
   no numpy interchange (opaque `ArmaMat`), so element access is slow but fine at emax ≤ 2.

**Notes from M1 (2026-11-12).** The golden data, their commands and formats are listed in
`tests/golden/README.md`. The 3N test file is a contact-only (cE) component (its T = 3/2 matrix
elements vanish), which makes the full IT-4/IT-5 Magnus flows diverge; IT-4/IT-5 therefore compare
the HF numbers and the flow stopped at s = 10 (`tests/golden/e2e/IT-4/smax10`, `IT-5/smax10`).
O16 at emax 2 is unstable in IMSRG(2) with this 2N interaction (any generator tried), so the
emax-2 part of IT-8 uses He4 (`e2e/IT-8/He4_emax2`); O16 is covered at emax 3. See M1-Q1.

## 5. Performance tracking

`tools/bench/` holds micro-benchmarks for the key kernels (comm222_ph, comm222_pp_hh, BCH
transform) at emax 4 and 6, and for the IMSRG(3) kernels at **emax 2 and 3 only**. Results (with commit hash, preset,
thread count) are appended to `design/benchmarks/*.md`. Compare against imsrg-devel timings
from the same machine. The goal is to be at least as fast on CPU before any GPU work.
